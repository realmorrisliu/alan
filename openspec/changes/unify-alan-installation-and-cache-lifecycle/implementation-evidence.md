## Managed output and cleanup — tasks 1.3–1.4

Producers hold inheritable shared file locks; cleanup needs exclusive access, unchanged ownership/inode, known Cargo entries, and an idle open-file scan before scoped `cargo clean`. Registered concurrent producers can share access; nested quality/installer processes retain the outer lease. Replaced/symlink/unknown directories fail closed. ## Disposable workflows and native Cargo cleanup — task 1.5

Disposable runs now require a separate evidence directory, record source SHA/dirty state, command, exit code and cleanup outcome, and retain combined diagnostics. They force `CARGO_INCREMENTAL=0` and keep intermediate output inside the selected task root. Cleanup runs only after command completion and release of the producer handles; busy descendants retain output. Interrupted runs retain initial/interruption evidence. Self-eval and repo-worker use unique run directories, no longer erase earlier runs, and never force-remove a changed worktree. Self-eval gives each profile its own autonomy report directory. Its CI job caches registry inputs only, since compiler output is disposable.

Real execution exposed two details beyond simulated build tests: creating a target before Cargo means Cargo does not create its cache tag; and full-directory Cargo 1.97 cleanup does not acquire native per-profile build locks. Newly registered empty roots now receive the standard CACHEDIR.TAG; cleanup requires the tag and explicitly acquires existing native profile locks in addition to the workflow lease. The open-file scan excludes the cleaner's own acquired handles. Missing tags remain a refusal, not an implicit repair. See the pinned [Cargo 1.97 cleanup implementation](https://raw.githubusercontent.com/rust-lang/cargo/rust-1.97.0/src/cargo/ops/cargo_clean.rs).

19 lifecycle tests and 5 installer fixtures pass using this repository's pinned toolchain, including abrupt producer termination with a surviving child, native-lock contention, missing tags, failure evidence retention and successful scoped retirement. Real repo-worker smoke passed; `target/repo-worker/smoke/run.CFhbdw/build-evidence/build.json` records successful removal of its compiler root with source/report retention. Real local self-eval passed twice; the final profile-isolated run is `target/harness/self_eval/run.297NFa/`, and both baseline/candidate evidence files record `cleaned`. The retained first implementation run is `run.bXIBtF`. Earlier failed cleanup experiments remain intentionally visible rather than being silently reclassified.

## Marked temporary service stores — task 2.5

Temporary Connection and Package Service construction (including bootstrap) now shares a small scoped store owner. It creates a private generated directory, writes a versioned marker with exact canonical path, device/inode, kind and creator PID, and retains a shared marker lock through directory cleanup. Persistent stores do not acquire this marker. The standard File locking API is already used by this repository.

`just cache-status` and preview/apply cleanup now also inspect only the new marked service-store prefix in the current Host temporary directory. Cleanup requires exclusive marker access, exact ownership identity, a dead PID, classified generated entries and no open consumer; a live/reused PID, symlink, replaced root, unknown marker/content or unavailable process scan retains the directory. Old per-PID Skill roots and unmarked legacy temporary files are excluded. This is not a durable-store migration or a home-directory sweep.

## Product access exclusion and pending receipt — partial task 3.4

A Host-owned installation access guard holds a shared native file lock for the complete data-using CLI invocation and legacy Host process entry point. Migration receives an exclusive guard. Bare startup, Connection commands (including metadata/auth operations), Skills commands and legacy cleanup/import acquire access before touching stores; processless help/version, status/stop and read-only legacy inspection remain available. Existing store owners keep their own write locks. This shared guard does not establish quiescence for older binaries, which must still be checked separately before migration publication.

The journal has a bounded, versioned schema with fixed publication component kinds, source selection, transaction UUID, state and fingerprints; no journal-supplied arbitrary destination path is accepted. Exclusive access supplies atomic journal replacement with file and parent-directory synchronization. Preparing/publishing receipts block ordinary access after the writer exits, and malformed/unknown receipts fail closed. The writer must retain exclusion through publication and only remove a receipt after verified rollback; the transaction orchestration and complete binding-level audit remain unfinished, so task 3.4 is still unchecked.

The platform data path resolves existing aliases before applying no-symlink checks to product paths, supporting macOS /var without accepting a symlinked product root or lock. All tests use temporary platform homes. Eight installation unit tests, three new subprocess integration tests and five existing legacy-state CLI integration tests pass. They verify concurrent shared access, exclusive exclusion, pending/committed receipt handling, malformed/oversized/duplicate receipts, symlink refusal, processless inspection and rejection before System/Host Store creation. Targeted all-target Clippy, formatting, source-size and diff checks passed. No migration operation has been wired to publish user data; source-writer checks, staging/resume/rollback, canonical bindings and full gates remain pending.

## Staging and explicit adoption orchestration — partial tasks 3.2–3.4

The new top-level `alan legacy-state` surface exposes `migrate-installation --from stable|dev`, `--dry-run`, and explicit `--rollback`, while the existing Host legacy-state alias remains during the transition. Legacy command dispatch was extracted without changing existing authored-import/cleanup behavior. There is no inferred source. Dry run validates offline without creating product locks, stores, staging or a journal; absent source and missing `--from` are covered by subprocess tests.

The transaction inventories regular files/directories with SHA-256, file lengths, POSIX mode and owner/group. It streams file bytes, preserves empty directories and mode bits, and excludes only the generated agent-runtime cache/tmp subtrees. Unknown/symlink/special files fail. Native source locks are retained without creating absent source lock files; production preflight checks current-user process names and open-file consumers with ps/lsof and fails closed when that evidence is unavailable. These checks do not replace the operator requirement to stop old versions, and their full real-process/platform qualification remains pending.

Under the product exclusive lock, a Preparing receipt precedes private per-filesystem staging. Staged owners validate offline; a Publishing receipt precedes fixed component renames; every source fingerprint is rechecked before publication. The final owner validation precedes Committed. Fixed stage roots are removed before commit; sources are retained. Committed retry performs no overwrite, different-source retry refuses, and rollback rejects changed or newly introduced canonical components. RollingBack remains a pending reader-blocking state across interruptions.

## Independent recovery inventory and real-process verification — task 3.2; partial 3.3–3.4

The preceding source-dependent rollback limitation is resolved. Before any component is staged, the exclusive migration owner persists a private, bounded recovery inventory outside the stores. It contains paths, POSIX metadata and content hashes, never credential bytes. Atomic no-replacement persistence, directory synchronization, no-follow reads and a 64 MiB bound protect this metadata. Loaded inventories validate root-relative paths, parent directory structure, file/directory records and the journal's component fingerprints before authorizing recovery.

Rollback now obtains its inventory from this durable record, without decoding or reconstructing old source contents. Editing or removing the retained source no longer prevents rollback of an unchanged canonical copy. Committed retry also verifies the persisted inventory. Missing/corrupt inventory with staged or published payloads fails closed and preserves data; the two metadata-only interruption windows (before inventory creation and after completed rollback removes it) can safely clear their receipt only when no migration payload remains. The inventory is retained after commit for explicit rollback and removed after successful rollback. Source retirement remains a separate operation.

23 migration library tests and 9 installation/guard unit tests pass, covering changed/removed old sources, every existing publication boundary, recovery metadata removal interruption, corrupt/missing inventories, escaping paths, private mode, no replacement, and symlink rejection. Explicit selection never merges the unselected source or a populated canonical destination; both dry-run and apply reject that conflict without creating a migration lock or journal. Task 3.2 is now checked on that evidence.
